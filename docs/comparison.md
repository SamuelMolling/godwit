# Comparison

godwit against Flyway, Liquibase and Atlas, as of the code on `main`. Written by the godwit side; the other columns come from their public documentation (linked at the end), not from running them. Where godwit lacks something, it says so.

godwit is narrower on purpose: PostgreSQL only, plain SQL only, and it is a service rather than a CLI. If you need another database, a DSL, or declarative schema-as-code, stop reading: it is not a fit.

Everything in the godwit column is covered by tests against real PostgreSQL in containers, and the crash paths by SIGKILLing replicas mid-statement. None of it has run against a production database yet: the rows say what godwit does, not what it has proven at scale.

## Feature by feature

| Capability | godwit | Flyway | Liquibase | Atlas |
|---|---|---|---|---|
| Databases | PostgreSQL | many | many | many |
| Migration format | plain SQL, up + down required, versioned (`<timestamp>_<name>`) or repeatable (`R__<name>`); a `-- godwit: <op> ...` comment line declares a change godwit builds the lock-safe statements for, or a data condition it checks | SQL, Java | XML/YAML/JSON/SQL changelogs | SQL, HCL, ORM-derived |
| Directives godwit executes | `change-type`, `backfill`, `add-column`, `add-not-null`, `add-index`, `drop-index`, `add-fk`, `add-check`, `drop-column`, `assert`. Parsed offline at load time (`E004`), then expanded at plan time on a scratch database carrying the target's replayed history — so the real primary key, column type, nullability and constraint names, not a guess — and frozen onto the plan and the run, so what applies is what the pull request showed. Expanded once: a migration the target already recorded keeps the expansion its own run froze. Everything godwit will not do safely is refused by name (partitioned table, identity or generated column, foreign-key member, `VOLATILE` `using=`, no batching key, a colliding `<c>_new`/`<c>_old`, ...) | no | change types (`addColumn`, `addNotNullConstraint`, ...) emit the direct DDL; no multi-step lock-safe rewrite | `-- atlas:` directives configure execution (`txmode none`) and linting; analyzers warn about the unsafe form, they do not replace it |
| Online column type change | `-- godwit: change-type users.age bigint`: add the column, keep both sides in sync with a trigger, backfill in resumable batches, then swap in a held contract phase, leaving `<c>_old` as a lossless rollback (`keep-old=false` opts out and says the phase is irreversible). Recorded in `cp_retired_columns` so `godwit diff` stops proposing to drop the rollback column | no | no | no; the analyzer warns about the rewrite, the safe form stays the author's |
| Batched backfill with a journalled cursor | one plan statement plus a batch spec, not N unrolled statements: each batch commits its rows and the new cursor in the same transaction, with a configurable size and pause. A kill mid-backfill resumes from the cursor — nothing redone, nothing skipped — and `rows_done`/`rows_total` ride on the run row, printed by `godwit run get` and on the line `migrate` and `run watch` stream | no | no | no |
| A backfill that is safe against concurrent writes | `-- godwit: backfill` installs a `BEFORE INSERT OR UPDATE` trigger for the length of the batches, so a row written below the cursor after the cursor passed it is written backfilled rather than left stale, and closes with a generated assertion that counts the rows still matching before the run may succeed. Everything the trigger could not honestly repeat — a `set=` that reads what it assigns, that assigns the batching key, that assigns a type with no equality operator, a subquery, another table's column, a `VOLATILE` function — is refused by name | no | no | no |
| Schema history | `godwit.migrations` and `godwit.repeatables` in the target, plus per-statement `godwit.runs`/`godwit.journal`; run history in the service store | `flyway_schema_history` | `DATABASECHANGELOG` | `atlas_schema_revisions` |
| Checksum validation | yes: applied version with a different checksum refuses; resume refuses if a statement's hash changed; `lint --base` flags edited merged files (`E003`, repeatables exempt) | `validate` | checksum on changesets | `atlas.sum` file |
| Repair / realign checksums | no `repair` command, and no dirty state to repair: a crashed run resumes from its journal and a crashed batch from its cursor; a re-run of the same pipeline job re-attaches to the run it already created instead of queueing a second; a pending migration whose effect is already on the target is *recorded* with zero statements instead of executed; `migrate --plan <id>` applies one reviewed plan explicitly; `BaselineTarget` adopts a database godwit did not build. What stays refused is a file whose checksum moved after it was applied — write a new migration | `repair` | `clearCheckSums` | `migrate hash` |
| Crash safety | statement-level journal with write-ahead intent for non-transactional statements; resume from the last done statement after any crash, and from the journalled cursor inside a batched statement | per-migration transaction where the DB allows; `failed` row needs `repair` | per-changeset; manual cleanup | per-file; `migrate status` shows partial |
| Locking | session advisory lock per target database, plus a lease per target in the service | lock on the history table (advisory lock on PostgreSQL) | `DATABASECHANGELOGLOCK` | advisory lock |
| Undo / down | required for every migration; `RevertRun` goes through the same gate and executor, and is scoped to the **ledger of what the run applied** (Liquibase `rollback-one-update` semantics), never to the directory it submitted. Default target is the newest un-reverted run and never anything wider — an older one takes `--force`; the plan is printed before it runs (`--dry-run` alone); a plan that would drop a table or column still holding rows is **refused**, not warned about (`--allow-data-loss`), and the revert is recorded as a new run rather than deleting history. A migration whose up side is a directive may write the single line `-- godwit: revert` and let godwit generate the inverse, which it refuses wherever the inverse would not be lossless (`drop-column`, `drop-index`, `backfill`, `keep-old=false`) | Undo migrations (paid tiers) | rollback (auto for some changes, manual for SQL) | down migrations (paid) |
| Dry run against a live database | `PlanRun` / `migrate --dry-run`: hazards and recipes, ordering, scratch validation, already-applied detection, phases, and the directive expansion the run would apply | `migrate -dryRunOutput` (paid) | `updateSQL` | `migrate apply --dry-run` |
| Plan as contract | `godwit plan --target` stores the admitted plan with an observation of the target (history hash, schema fingerprint, `search_path`) keyed on the pending set; `migrate` binds to it, re-plans by itself when every change is explained by another run, and refuses with the exact diff when it is not. `require_plan` makes a stored plan mandatory; `godwit plans` / `plan show <id>` read them back; `--plan-retention` prunes bound and superseded ones | no | no | `schema plan` stores an approved plan in Atlas Registry and uses it only on a database matching its `from` fingerprint (declarative flow) |
| Pre-flight validation | replays the target's whole recorded history plus the new files on a scratch database before queueing | none built in | preconditions | `migrate lint` with dev database replay |
| Lint / safety analysis | `H001`–`H010` (PostgreSQL DDL hazards), each carrying the safe form as ready-to-copy SQL, and the equivalent `-- godwit:` directive wherever the grammar expresses it exactly; `E001` load, `E002` parse, `E003` edited after merge, `E004` malformed or misplaced directive, `E005` the committed SQL no longer matches the ORM schema, `W001` no-op down, `W002` not checked (no server). Hazard acknowledgement is part of the run request | none in Community | policy checks (Pro) | analyzers (destructive, data-dependent, concurrent index, ...) |
| Drift detection | fingerprint after every successful run, periodic monitor, events, accept | drift check (Community preview since 10.20) | `diff` command | `schema diff` / `schema inspect` |
| Expand/contract rollout | built in, and split by **statement**: `expand-contract` applies the additive statements, parks the run in `awaiting_contract`, and `ConfirmRollout` resumes the *same* run from the statement it stopped at. A hand-written migration still splits at the migration boundary; a directive splits inside one migration | no | no | no |
| Out-of-order migrations | refused unless `--allow-out-of-order` | refused unless `outOfOrder=true` | allowed by default | refused by default (`--exec-order`) |
| Baseline an existing database | `BaselineTarget` (target's journal must be empty) | `baseline` | `changelogSync` | `migrate set` |
| Target version (`--to`) | `--to <version>` on `plan` and `migrate`: the whole directory is still submitted and validated, only the migrations at or below the version run, and the rest are stored on the plan and printed in the pull-request comment as **withheld**, so the reviewer cannot mistake the plan for the whole set. Repeatables are held back with them and run once nothing is. Refused by name: a version the directory does not hold, one behind what the target has applied (`--to` never reverts), one selecting nothing while work above it is pending, and `--to` on top of `--plan` | `-target` | `update-to-tag`/count | `migrate apply N` |
| Repeatable migrations | `R__<name>.up.sql` + `.down.sql`: no version, applied after the run's versioned files when the checksum differs from `godwit.repeatables`, part of the plan key and the hazard gate; no `runAlways` | `R__` migrations | `runOnChange` / `runAlways` | no |
| Placeholders / templating | no; template in the pipeline | placeholders | properties | template dirs |
| Data assertions | `-- godwit: assert 'SELECT count(*) FROM orders WHERE total IS NULL' = 0`: a condition about the data, parsed offline as a single read-only `SELECT`, rendered in `godwit plan` and in the pull-request comment as a statement of its own, executed inside the run in a read-only transaction and journalled like any other statement. Placed before the migration's SQL it is a precondition; placed after a `change-type` or `backfill` it is the last statement of the expand phase, so a failed condition stops the run before the swap and `ConfirmRollout` re-checks it against the data as it is at confirm time | no | preconditions on a changelog or changeset (`sqlCheck`, `tableExists`, ...), with `onFail` policies; they gate the changeset, not a phase of it | no |
| SQL hooks (before/after) | no, deliberately: an opaque hook would run SQL the pull request never showed. `-- godwit: assert` is the in-plan answer for a data condition; webhook and Slack notifications are the operational one | callbacks | not built in | no |
| `search_path` per target | `--search-path app,public` on the target: every session (run, revert, plan, diff, scratch validation) sets it; journal stays schema-qualified in `godwit` and `godwit` is refused on the path | `schemas` | `defaultSchemaName` | `--schema` |
| Contexts / labels | no; use targets and directories | no | yes | no |
| Tag and rollback-to-tag | no; reverts are per run, newest run first and newest migration first within it | no | `tag`, `rollback <tag>` | no |
| Checkpoints | `godwit checkpoint`: one file carrying the schema every version below it produces, marked `-- godwit: checkpoint through=<version>`. It is generated from a scratch replay of the files, never from a live target, and refused unless applying the generated body alone reproduces the same schema fingerprint. A database with no history runs it and records what it collapses; every other database records it and runs nothing of it; a scratch replay starts from the newest checkpoint the target holds and never replays below it. What is given up is stated and enforced: below a checkpoint nothing can be reverted, and a target parked below one whose collapsed files are gone from the directory is refused by name | no | no | `atlas migrate checkpoint` (Pro); same file-in-the-directory shape, used to speed up setting up a database from scratch |

The before side is the live target by default, or the committed migrations replayed on a scratch database (`base = files`), which is what `lint` compares against. The desired side is the schema plus the directory's `R__` migrations, so what a repeatable declares is never proposed as a drop and a diff that cannot see the directory is refused; a `change-type`'s retired column is kept out of the generated `up` | no | `diff-changelog` | `migrate diff` (schema in HCL, SQL or from an ORM; dev database) |

## What godwit does not have, and why

- **A retention command.** Plans are swept on the service's own ticker, but runs, `cp_run_files`, drift events and audit rows are not: growth is one journal row per statement and one file body per run, and the SQL to prune is in [operations](operations.md#retention).
- **SQL hooks.** Notifications are the operational hook. Arbitrary SQL before or after a run stays refused: it would run outside the plan, which is the one promise godwit makes. The case hooks were asked for — checking a data invariant — is [`-- godwit: assert`](concepts.md#assertions), which is *in* the plan: parsed offline, rendered on the pull request, journalled, and read-only by construction. A hook that has to write is a migration.
- **A declarative apply.** `godwit diff` generates the migration from a desired schema, but what runs is always a versioned file that went through the gate, and the output has holes (domains, composite types, exclusion constraints, comments, roles) that Atlas does not have. It is a shortcut for writing the file, not a replacement for the history.
- **A checkpoint that collapses repeatables or data.** A checkpoint carries the versioned schema only. `R__` files are never collapsed — their identity is their body, and they re-apply on top of the checkpoint as they always did — and no `INSERT` a collapsed migration ran survives into it, exactly as in Atlas. A history whose migrations seed rows needs those rows written into the checkpoint by hand, or kept out of it with `--at`.
- **A `repair` command.** Deliberate, and the *Repair / realign checksums* row is the whole answer: the states other tools repair — a half-applied migration, a run nobody knows the state of, a schema someone changed by hand, a duplicate run from a re-run job — are resumed, re-attached, recorded or baselined instead. The one thing godwit refuses to paper over is a file edited after it was applied.
- **Directives for `rename-column`, `rename-table` and `drop-table`.** A safe rename needs the application to read either name during the transition. pgroll buys that with versioned views over the physical table; godwit's unit is a versioned SQL file and it will not start owning the application's view of the schema. `add-column` + `backfill` + `drop-column` expresses the same change in three reviewable migrations, with the expand/contract gate between them.
- **A two-version window.** Following from the above: godwit does the physical work and holds the contract phase until a human confirms, but the window where old and new application code coexist is the deployment's problem, not godwit's.
- **Multiple databases.** The planner is `libpg_query`; every hazard is a PostgreSQL lock or rewrite semantics. Nothing here ports.

## What godwit has that the others do not, in one line each

Statement-level crash recovery with verified resume of `CREATE INDEX CONCURRENTLY` and of a batched backfill from its journalled cursor; a `-- godwit:` directive expanded against the target's own catalog into lock-safe statements and frozen into the reviewed plan; expand/contract split by statement, so one migration can be held mid-way and resumed as the same run; apply before merge with a commit status that stays pending until the contract phase has run; a hazard gate with acknowledgement as part of the run request; scratch-database replay of the full history before admission, reused to tell whether the committed SQL still matches the ORM model; and a leased multi-replica service with scoped tokens, audit, drift monitoring and an operator UI in the same binary.
