# Comparison

godwit against Flyway, Liquibase and Atlas, as of the code on `main`. Written by the godwit side; the other columns come from their public documentation (linked at the end), not from running them. Where godwit lacks something, it says so.

godwit is narrower on purpose: PostgreSQL only, plain SQL only, and it is a service rather than a CLI. If you need another database, a DSL, or declarative schema-as-code, stop reading: it is not a fit.

Everything in the godwit column is covered by tests against real PostgreSQL in containers, and the crash paths by SIGKILLing replicas mid-statement. None of it has run against a production database yet: the rows say what godwit does, not what it has proven at scale.

## What godwit does not have, and why

- **`--to <version>`.** Send fewer files. A client-side filter is planned; the service does not need to change.
- **A retention command.** Plans are swept on the service's own ticker, but runs, `cp_run_files`, drift events and audit rows are not: growth is one journal row per statement and one file body per run, and the SQL to prune is in [operations](operations.md#retention).
- **SQL hooks.** Notifications are the operational hook. Running SQL before or after a run needs a design decision (per run or per migration) that has not been taken.
- **A declarative apply.** `godwit diff` generates the migration from a desired schema, but what runs is always a versioned file that went through the gate, and the output has holes (domains, composite types, exclusion constraints, comments, roles) that Atlas does not have. It is a shortcut for writing the file, not a replacement for the history.
- **Checkpoints.** Validation replays the full recorded history; on a long history that becomes slow. Baselining a target resets the replay root and covers the same need until it does not.
- **A `repair` command.** Deliberate, and the *Repair / realign checksums* row is the whole answer: the states other tools repair — a half-applied migration, a run nobody knows the state of, a schema someone changed by hand, a duplicate run from a re-run job — are resumed, re-attached, recorded or baselined instead. The one thing godwit refuses to paper over is a file edited after it was applied.
- **Directives for `rename-column`, `rename-table` and `drop-table`.** A safe rename needs the application to read either name during the transition. pgroll buys that with versioned views over the physical table; godwit's unit is a versioned SQL file and it will not start owning the application's view of the schema. `add-column` + `backfill` + `drop-column` expresses the same change in three reviewable migrations, with the expand/contract gate between them.
- **A two-version window.** Following from the above: godwit does the physical work and holds the contract phase until a human confirms, but the window where old and new application code coexist is the deployment's problem, not godwit's.
- **Multiple databases.** The planner is `libpg_query`; every hazard is a PostgreSQL lock or rewrite semantics. Nothing here ports.

## What godwit has that the others do not, in one line each

Statement-level crash recovery with verified resume of `CREATE INDEX CONCURRENTLY` and of a batched backfill from its journalled cursor; a `-- godwit:` directive expanded against the target's own catalog into lock-safe statements and frozen into the reviewed plan; expand/contract split by statement, so one migration can be held mid-way and resumed as the same run; apply before merge with a commit status that stays pending until the contract phase has run; a hazard gate with acknowledgement as part of the run request; scratch-database replay of the full history before admission, reused to tell whether the committed SQL still matches the ORM model; and a leased multi-replica service with scoped tokens, audit, drift monitoring and an operator UI in the same binary.
